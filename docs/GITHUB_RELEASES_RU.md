## Следующие обновления Android

1. Увеличить `versionCode` и назначить новую версию. Для текущего встроенного
   обновлятора использовать `X.Y.Z-beta` и тег `mit-beta-X.Y.Z`.
2. Собрать и проверить APK из зафиксированного коммита. Использовать сохранённый
   постоянный ключ через GitHub Secrets. Не включать keystore, Base64 ключа,
   пароли или приватный JSON в репозиторий и артефакты.
3. Создать черновик предварительного выпуска на нужном коммите. Описать изменения,
   совместимость и ограничения по [шаблону](../.github/RELEASE_TEMPLATE_RU.md).
4. Приложить `mits-vpn.apk`, `mits-vpn-update.json`, `SHA256SUMS` и
   `certificate-sha256.txt`. Манифест должен содержать схему 1, прежний
   `application_id`, новую версию и номер сборки, фактические размер и SHA-256 APK.
5. Проверить подпись, идентификатор приложения, версию, состав файлов, контрольные
   суммы загруженных файлов и целевой коммит тега. Затем опубликовать выпуск.
6. Проверить публичные ссылки без авторизации, доступность манифеста и обновить
   ссылки и описание в README. Убедиться, что исходники доступны по тегу.

Опубликованный APK не заменять другим файлом под тем же тегом: исправления
выпускать с новым номером сборки и версией.

Встроенный поиск читает опубликованные релизы, включая предварительные.
Он предлагает только сборку с большим номером. Загрузка и установка требуют
действия пользователя; Android допускает обновление поверх при совместимой подписи.

## Особенности текущей публикации

Workflow `publish-existing-android-beta.yml` предназначен только для проверенного
выпуска 50006: он закрепляет исходный коммит, задание подписи, хеш APK и черновик.
Он не является автоматическим издателем будущих версий. Повторный запуск после
публикации остановится на проверке черновика и не заменит публичные файлы.

Главная страница `main` оформлена отдельно от кода платформенных веток.
Windows-выпуски следует собирать из Windows-ветки, указывать архитектуру,
формат установщика и результаты проверки запуска и подключения на Windows.
