# Техническое задание — Mit VPN, MVP для Android

## Цель
Превратить форк Hiddify в собственный VPN-клиент: **одна кнопка подключения**, однократная активация, автоматическая маршрутизация. После Android — iOS и Windows из той же Flutter-кодовой базы.

## Что уже есть
- Flutter-приложение Hiddify и существующий VPN-движок.
- Пользователь располагает отдельным сервером Xray, протокол VLESS + REALITY + TCP, flow `xtls-rprx-vision`. Состояние/точные параметры сервера в этом репозитории не подтверждены.
- Сначала реализуем приложение и проверим его с **тестовой подпиской**, а не переносим реальные секреты в Git.

## Сценарий пользователя
1. Открывает приложение впервые.
2. Вводит одноразовый код активации или сканирует QR, который безопасно привязывает **персональную** подписку. Для локального MVP допустим импорт безопасной тестовой подписки вручную.
3. Видит главный экран «Подключиться» с текущим состоянием.
4. Нажимает кнопку: приложение запрашивает системное разрешение VPN, подключает TUN и активирует маршрутизацию.
5. Российские сайты и частные сети идут напрямую, остальной доступный интернет — через VLESS + REALITY; исключения и обновления правил приходят централизованно.
6. После перезапуска настройки сохраняются; ошибки подключения понятны пользователю.

## Маршрутизация (политика, а не безусловная гарантия)
- `private` / локальные адреса -> DIRECT.
- RU-domain policy + RU-IP GeoIP -> DIRECT, с явными списками исключений и приоритетов.
- Всё остальное -> PROXY, без скрытого fallback в DIRECT.
- DNS для маршрутизации по доменам и IP должен быть согласован, IPv6 учтён; при проблеме маршрутизации не направлять зарубежные запросы в обход туннеля.
- GeoIP не равен принадлежности сервису: зарубежный CDN может обслуживать российский сайт и наоборот. Не путать определение по домену и геолокации IP.
- Не использовать бездумно правило «все .ru всегда DIRECT»: поддомены и внешние хостинги требуют исключений; поддержать списки приоритета.

## Android MVP — приоритеты
**P0:** сохранить рабочую сборку; минимальный главный экран; подключение/отключение; безопасное сохранение профиля; тестовое подключение.
**P1:** политика split tunneling, DNS и защита от утечек; импорт/обновление подписки; диагностика.
**P2:** автообновления rule-set, QR активация, сборка подписанного APK, собственный бренд.

## Требования к интерфейсу
- Домашний экран: крупная кнопка, чёткое состояние: «Не подключено», «Подключение…», «Подключено», «Ошибка».
- Под кнопкой: активный сервер/режим, краткие сведения о маршрутизации, пункт «Настройки».
- Продвинутые настройки скрыты, но не безвозвратно удалены; сделать доступным экран диагностики и восстановления.
- Дизайн русскоязычный, пригодный для тёмной/светлой темы.

## Активация/управление
Отдельный backend для выдачи персональных подписок **проектируется позже**. Не предполагать, что текущий Xray предоставляет HTTP API. Не хранить мастер-ключи в клиенте. Для MVP допустим персональный URL подписки, доставленный вне репозитория. Требования: HTTPS, возможность отзыва, персонификация, безопасное хранение.

## Критерии приёмки
- Android debug/release собираются при заявленном SDK без коммитов секретов.
- После однократной настройки пользователь подключается одной кнопкой.
- Реальные Android VPN разрешения и TUN работают, не только смена текста на экране.
- Тесты маршрутизации: RU direct; non-RU proxy; RFC1918 direct; DNS split; IPv4/IPv6; отключение/ошибка VPN; перезагрузка; нестабильная сеть.
- Клиент не показывает чувствительную информацию в логах.
- Проверено, что проект не нарушает условия исходных лицензий.
- В PR описаны тесты и известные ограничения.

## Этапы
1. Android (MVP).
2. Windows (системный VPN/TUN и инсталлятор).
3. iOS (Apple Developer, Network Extension, подпись и TestFlight).

Никакой реальный Xray сервер в процессе выполнения задания не менять.
